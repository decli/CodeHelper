# 取件码助手（CodeHelper）

一款为老人场景设计的本地短信取件码助手。

## 功能

### 首页：一眼看到还有几个包裹

- 打开就读最近 12 小时的短信，只展示还没取的取件码
- 待取数量用 104sp 大数字直接落在页面上（数字为 0 时变松绿），右侧是可点开的时间范围胶囊
- 待取包裹按驿站分组，同一家店的包裹排在一起（可在设置里关掉）
- 取件码卡片只保留一件正事：一个松绿「我已取到」大按钮，下面是「看短信 / 复制 / 读给我听」三个文字按钮；短信正文与识别依据已从卡片移除
- 已取件降为一行摘要（松绿对勾 + 灰色取件码 + 「恢复」），只在「全部包裹」标签的末尾出现
- 「我已取到」不弹确认框：卡片收起、数字减少，底部提示条 6 秒内可一步撤销

### 点一下取件码 = 全屏出示

- 点取件码进入全屏出示页，字号最大 150sp，屏幕临时调到最亮并保持常亮，方便在柜台前给工作人员看
- 出示页可直接复制、朗读、标记「我已取到」，标记后自动回到首页并给出撤销机会

### 读给我听

- 取件码逐字朗读（`3-3-06006` 读成「3 杠 3 杠 0 6 0 0 6」），语速 0.75×，再点一次停止
- TalkBack 读屏与语音播报口径一致，不会把取件码按整数念
- 本机没有语音引擎时按钮变灰但不隐藏，点按会给出提示

### 取件码永远看得清

- 每个取件码渲染成独立的单行文本，一码一行、永不折行、不省略
- 字号用 `TextMeasurer` 逐档实测，取「最长的码单行放得下」的最大值（上限 104sp，「特大」档 119sp，出示页 150sp）；码区左右只留 4dp，把宽度全部让给字号
- 取件码字重固定 800：系统中文字体多数没有真实的 900 字面，用 900 会被合成加粗，笔画糊、字碗被填小，深色模式下更难认
- 同一张卡里的多个取件码共用同一字号，逐行展示

### 时间范围

- 默认「最近 12 小时」，点胶囊打开面板，可选 12 小时到 14 天共 7 档
- 面板里每一档都显示「N 件待取」，不用逐档试

### 首次启动引导

- 三步引导，每步只讲一件事：为什么需要短信权限、通知权限能带来什么，都在弹系统权限框之前先说清楚
- 老用户升级不会再看到引导

### 设置：改了就存

- 去掉「保存并刷新」按钮，每一项改动立刻生效
- 新增「显示」分组：取件码字号（标准 / 特大）、外观（跟随系统 / 浅色 / 深色）、按驿站分组开关
- 识别提示词改成一排大芯片，点一下开关，「＋ 新增」用大字号输入框添加
- 正则规则收进「高级」折叠区，普通用户不会碰到；语法错误只让那一条不生效，红字提示，其它设置照常可用
- 桌面角标刷新频率用 5 / 10 / 15 / 30 分钟四个大按钮选择，自由输入留在高级区

### 看得清

- 全应用字阶按适老化标准整体上调：正文 18sp、可操作文字 ≥19sp、最小字号 16sp，不再出现 14sp 与 12sp
- 正文字重 500 起步：深色模式下细笔画容易发虚，加粗一档比单纯放大更清楚
- 卡片里「看短信 / 复制 / 读给我听」改为图标在上、文字在下的 64dp 按钮，系统字号放大到 1.3× 也不会截断

### 底层能力（与 v1.3 一致）

- 同时读取本机 `SMS + MMS`，只展示收到的消息，不展示本机发出的短信
- 待取数量按未取件的实际取件码条数累加，同一条短信里有 3 个码就计 3 个
- 桌面图标角标显示待取数量，默认每 5 分钟刷新
- 默认在「取件码」「提货码」「货码」「驿站码」「凭」等提示词后面识别取件码，兼容 `取件码为`、`凭“1-3-27017”`、`货码为3-3-06006，8-5-06003` 等写法
- 全程离线运行，不申请网络权限

### 设计规范

界面遵循 `docs/ui-design-spec-v1.4.md`（「柿柿如意」v1.4）：色彩与字阶令牌、间距圆角、组件三级按钮、交互与动效上限、12 项适老化 / 无障碍检查表。
设计交付包（可点击原型、可视化规范、现状对照、可用性测试脚本）在 `docs/design/v1.4/`，本次实现说明与规范偏差记录在 `docs/ui-redesign-v1.4.md`。

## 权限说明

- 应用核心读取能力以 `v1.0.12` 代码版本为准，不再要求用户将应用设置为默认短信应用
- Android 13 及以上系统需要允许通知权限后，桌面角标数字才会显示；不同桌面启动器可能会显示数字角标或通知圆点
- 部分厂商系统会将物流平台短信归类为“通知类短信”或类似受保护通道。以小米系统为例，除普通短信读取授权外，还需要在系统设置中额外开放此类通知短信访问权限，否则系统短信列表里可见的物流消息仍可能无法被应用读取
- 如果复制同一条短信内容后由本机号码重新发送，应用可以识别，而原始平台短信无法识别，通常就是厂商短信权限分流导致，不是取件码正则规则本身的问题

## 构建发布

本仓库正式交付以 GitHub Actions 为准：

- 推送到 `main`：跑单元测试 + 构建 Release APK，并以 `v{versionName}` 发布正式版本
- 推送 `v*` 标签：在 Releases 页面创建对应正式版本并附带可下载 APK
- 推送 `claude/**` 特性分支：同样跑单元测试与构建，并把 APK 作为 `v{versionName}-preview.{run}` **预览版**发布到 Releases 页面，供验收阶段直接下载；预览版标记为 prerelease，不占用正式版本号

## 发布签名配置（升级安装必读）

**问题背景**：`v1.1.1` 及更早版本的 CI 在每次构建时现场生成一个新的签名密钥，导致每个版本的 APK 签名都不同。Android 要求升级包与已装应用签名一致，因此旧版本用户覆盖安装新版会报「应用未安装 / 与已安装应用签名不一致」（`INSTALL_FAILED_UPDATE_INCOMPATIBLE`），只能先卸载旧版再安装。

现在的 workflow 已改为优先使用仓库 Secrets 中的**固定签名密钥**。维护者只需一次性完成以下配置：

1. 在本地生成正式密钥库（密码请换成自己的，并妥善保管该文件——**丢失后将再次无法覆盖升级**）：

   ```bash
   keytool -genkeypair -v \
     -keystore codehelper-release.keystore \
     -alias codehelper \
     -keyalg RSA -keysize 2048 -validity 36500 \
     -storepass '你的密码' -keypass '你的密码' \
     -dname "CN=CodeHelper,O=CodeHelper,C=CN"
   ```

2. 把密钥库转成 base64 文本（macOS 用 `base64 -i codehelper-release.keystore | tr -d '\n'`）：

   ```bash
   base64 -w0 codehelper-release.keystore
   ```

3. 到 GitHub 仓库 `Settings → Secrets and variables → Actions` 添加 4 个 Repository secret：

   | Secret 名称 | 值 |
   | --- | --- |
   | `RELEASE_KEYSTORE_BASE64` | 第 2 步输出的 base64 文本 |
   | `RELEASE_STORE_PASSWORD` | 密钥库密码 |
   | `RELEASE_KEY_ALIAS` | `codehelper` |
   | `RELEASE_KEY_PASSWORD` | 密钥密码 |

4. 重新触发一次发布。**注意**：从「临时密钥版本」升到「固定密钥后的第一个版本」仍需最后卸载一次旧版；此后所有版本都能直接覆盖安装升级。

未配置 Secrets 时 workflow 仍会回退为一次性密钥并在构建日志里给出警告，便于 fork 仓库跑通构建，但产出的 APK 不具备可升级性。

另外两个覆盖安装的必要条件（workflow 已满足/需人工遵守）：每次发版 `versionCode` 必须递增；不要用低版本覆盖高版本。
